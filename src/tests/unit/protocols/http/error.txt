fuzzer-out http

#
#  Duplicate Content-Length headers with conflicting values.
#
#  RFC 9110 §5.2 treats multiple same-name header fields as equivalent to a
#  single field with their values joined as a comma-separated list.  RFC 9112
#  §6.3(5) requires a recipient to reject a message with an invalid
#  Content-Length, which includes a combined list whose values are not all
#  identical (e.g. "5, 10").  A server MUST reject such a message as malformed.
#
#  POST /test HTTP/1.1\r\n
#  Content-Length: 5\r\n
#  Content-Length: 10\r\n
#  \r\n
#  hello
#
decode-proto 50 4f 53 54 20 2f 74 65 73 74 20 48 54 54 50 2f 31 2e 31 0d 0a 43 6f 6e 74 65 6e 74 2d 4c 65 6e 67 74 68 3a 20 35 0d 0a 43 6f 6e 74 65 6e 74 2d 4c 65 6e 67 74 68 3a 20 31 30 0d 0a 0d 0a 68 65 6c 6c 6f
match ERROR: Duplicate Content-Length headers with conflicting values

#
#  RFC 9112 §2.2: "A recipient of such a bare CR MUST consider that element
#  to be invalid".  A bare CR (not immediately followed by LF) embedded in
#  the request line must be rejected, not silently absorbed into the path.
#
#  GET /pa<CR>th HTTP/1.1\r\n
#  \r\n
#
decode-proto 47 45 54 20 2f 70 61 0d 74 68 20 48 54 54 50 2f 31 2e 31 0d 0a 0d 0a
match ERROR: Malformed HTTP request line: contains a bare CR

#
#  Same rule, but the bare CR is embedded in a header line instead of the
#  request line.  Without this check, "bar<CR>Evil: header" would be decoded
#  as a single Header Value containing a raw CR byte.
#
#  GET / HTTP/1.1\r\n
#  X-Foo: bar<CR>Evil: header\r\n
#  \r\n
#
decode-proto 47 45 54 20 2f 20 48 54 54 50 2f 31 2e 31 0d 0a 58 2d 46 6f 6f 3a 20 62 61 72 0d 45 76 69 6c 3a 20 68 65 61 64 65 72 0d 0a 0d 0a
match ERROR: Malformed HTTP header line: contains a bare CR

#
#  RFC 9112 §2.2: "A sender MUST NOT generate a bare CR ... within any
#  protocol elements".  We reject LF too, since a full CRLF embedded in a
#  policy-controlled value would let it forge an extra header/status line
#  on the wire (response splitting).  Each field that reaches the wire is
#  checked: Path, Header Name, Header Value, and Reason-Phrase.
#
encode-proto Request = { Method = GET, Path = "/a\r\nX-Injected: evil", Version = HTTP-1-1 }
match ERROR: HTTP Request Path contains a CR or LF

encode-proto Response = { Version = HTTP-1-1, Status-Code = 200, Reason-Phrase = "OK\r\nX-Injected: evil" }
match ERROR: HTTP Response Reason-Phrase contains a CR or LF

encode-proto Response = { Version = HTTP-1-1, Status-Code = 200, Reason-Phrase = "OK" }, Header = { Name = "X-Foo\r\nX-Injected", Value = "bar" }
match ERROR: HTTP Header Name contains a CR or LF

encode-proto Response = { Version = HTTP-1-1, Status-Code = 200, Reason-Phrase = "OK" }, Header = { Name = "X-Foo", Value = "bar\r\nX-Injected: evil" }
match ERROR: HTTP Header Value contains a CR or LF

#
#  RFC 9112 §5.1: a header line beginning with whitespace is obsolete line
#  folding.  It MUST be rejected (or ignored entirely) rather than parsed as
#  an ordinary header field with a leading space folded into the name, since
#  a downstream recipient that instead treats it as a continuation of the
#  previous field's value would parse this message differently.
#
#  GET / HTTP/1.1\r\n
#  X-Foo: bar\r\n
#  <SP>X-Injected: evil\r\n
#  \r\n
#
decode-proto 47 45 54 20 2f 20 48 54 54 50 2f 31 2e 31 0d 0a 58 2d 46 6f 6f 3a 20 62 61 72 0d 0a 20 58 2d 49 6e 6a 65 63 74 65 64 3a 20 65 76 69 6c 0d 0a 0d 0a
match ERROR: Malformed HTTP header line: begins with whitespace (obsolete line folding)

#
#  Same rule, with a leading HTAB instead of SP.
#
#  GET / HTTP/1.1\r\n
#  X-Foo: bar\r\n
#  <TAB>X-Injected: evil\r\n
#  \r\n
#
decode-proto 47 45 54 20 2f 20 48 54 54 50 2f 31 2e 31 0d 0a 58 2d 46 6f 6f 3a 20 62 61 72 0d 0a 09 58 2d 49 6e 6a 65 63 74 65 64 3a 20 65 76 69 6c 0d 0a 0d 0a
match ERROR: Malformed HTTP header line: begins with whitespace (obsolete line folding)

#
#  A packet containing nothing but empty lines has no request-line to find,
#  even after RFC 9112 §2.2's leading-empty-line tolerance consumes them.
#
decode-proto 0d 0a 0d 0a
match ERROR: HTTP packet is empty

#
#  RFC 9112 §5.1: "No whitespace is allowed between the field name and
#  colon.  In the past, differences in the handling of such whitespace have
#  led to security vulnerabilities in request routing and response
#  handling.  A server MUST reject ... any received request message that
#  contains whitespace between a header field name and colon."
#
#  GET / HTTP/1.1\r\n
#  X-Foo : bar\r\n
#  \r\n
#
decode-proto 47 45 54 20 2f 20 48 54 54 50 2f 31 2e 31 0d 0a 58 2d 46 6f 6f 20 3a 20 62 61 72 0d 0a 0d 0a
match ERROR: Malformed HTTP header line: whitespace between field name and colon

#
#  Same rule, with a HTAB instead of a SP before the colon.
#
#  GET / HTTP/1.1\r\n
#  X-Foo\t: bar\r\n
#  \r\n
#
decode-proto 47 45 54 20 2f 20 48 54 54 50 2f 31 2e 31 0d 0a 58 2d 46 6f 6f 09 3a 20 62 61 72 0d 0a 0d 0a
match ERROR: Malformed HTTP header line: whitespace between field name and colon

#
#  RFC 9112 §3.2: "A server MUST respond with a 400 (Bad Request) status
